## CONTEXT

REST ENGINE is a music production system for Radical Noface — 5 color-based identities, each a rap × techno hybrid. JSON remains source of truth for engine rules/SDM. SQLite is now the operational data layer for beats, tracks, uploads, and daily pipeline.

Schema file `rest_engine_schema_v2.sql` and seeded database `rest_engine.db` are provided alongside this document. Copy both to project root before starting.

## 5 IDENTITIES (seeded in DB)

| Color | Surname   | Hybrid                      | BPM       |
|-------|-----------|-----------------------------|-----------|
| green | Cypress   | boom bap × dub techno       | 82–98     |
| grey  | Ember     | drill × industrial techno   | 138–145   |
| blue  | Tide      | cloud rap × melodic techno  | 72–108    |
| cream | Ize       | neo-soul × deep house       | 78–118    |
| black | Nightfall | rave techno (pure)          | 140–160   |

Each identity row contains: rap/techno genres, mood, energy, vocal character, key signatures, instrumentation (rap + techno + shared), full mix/master profile (mix character, stereo width, reverb profile, low-end, high-end, compression style), suno base prompt, negative prompt.

## TWO-PHASE EXECUTION PLAN

### PHASE 1 — SQL Backend (do this first)

**Step 1: db_manager.py**
- Single entry point for all DB operations (like sdm_tool.py is for SDM)
- CRUD for all 8 tables
- Key functions:
  - `add_beat(identity_id, suno_prompt, bpm, key, ...)` → insert + pipeline_log
  - `update_beat_status(beat_id, new_status, reason=None)` → status transition + log
  - `add_track(identity_id, album_id, beat_id, title, lyrics, ...)` → insert + log
  - `get_beats_by_status(status, identity_id=None)` → filtered query
  - `get_identity_profile(color)` → full identity row as dict
  - `create_daily_queue(date)` → generate 5 entries (one per identity)
  - `log_action(entity_type, entity_id, action, details)` → pipeline_log insert
- All writes go through this module. No raw SQL elsewhere.

**Step 2: prompt_engine.py**
- Reads identity profile from DB via db_manager
- Generates suno prompt variations from base template
- Variation strategies: BPM shift (±5), mood shift, instrument swap, energy shift
- Output: ready-to-paste suno style prompt + negative prompt
- Key functions:
  - `generate_beat_prompt(color, variation_type=None)` → prompt string
  - `generate_track_prompt(color, lyrics_theme=None)` → prompt string
  - `save_prompt_template(identity_id, prompt_type, style, negative)` → store in suno_prompts table
- Every generated prompt gets logged in suno_prompts with times_used counter

**Step 3: daily_pipeline.py**
- Creates daily queue: 5 beats, one per identity
- Selects or generates prompt for each
- Status flow: pending → generated → reviewed → done/skipped
- Key functions:
  - `init_daily_queue()` → populate daily_queue for today
  - `process_queue_item(queue_id, suno_url, ...)` → mark generated, create beat record
  - `review_beat(beat_id, approved: bool, reason=None)` → approve or reject
  - `get_today_status()` → summary of today's queue

**Step 4: Validation**
- Run full cycle: create queue → generate prompts → simulate beat entries → approve/reject → verify pipeline_log
- Confirm all foreign keys, indexes, status transitions work

### PHASE 2 — TUI Dashboard (after Phase 1 is solid)

Integrate SQL backend into Textual TUI dashboard (design from MIRAS_20260318_v2):

- **Beat Queue Panel** — today's daily_queue, status per identity, color-coded
- **Beat Browser** — filter by identity/status, approve/reject inline
- **Track Manager** — album progress, link beats to tracks
- **Pipeline Log** — live feed of all actions
- **Prompt Panel** — generate/preview suno prompts per identity
- **Stats View** — beats per identity, approval rate, upload count

Dashboard reads/writes exclusively through db_manager.py. No direct SQL in TUI code.
